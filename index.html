How to use this guide

Welcome to your Cyber Threat Monitoring Level 1 Capstone. Over five days your team will build a small security lab, switch on Windows logging, connect it to the Wazuh SIEM, investigate a simulated intrusion, and present your findings like a real Security Operations Center (SOC).

This is a guided capstone. Follow the days in order. Every step tells you exactly what to click or type, and every day ends with a checkpoint you can tick off.

One folder for everything. All files you need are in the CAPSTONE_RESOURCES folder that came with this guide. Upload that one folder to your team's shared drive (Google Drive, OneDrive, or Teams). Nobody needs anything else.
Safety first. Run every script and command only inside your lab virtual machines - never on your personal or work computer. The Day 4 "attack" is a harmless simulation. No real malware is used.

Legend used in this guide

CHECKHow to confirm the step worked.
TIPHelpful advice or a shortcut.

1. Capstone overview

What you will build

A two-machine lab inside VirtualBox:

  • CTM-WIN01 - a Windows workstation (the "victim"), with Windows auditing, Sysmon, and a Wazuh agent.
  • CTM-Wazuh - the Wazuh all-in-one server (manager + indexer + dashboard), which collects and analyses the logs.

Learning outcomes

By the end, every team member can:

  • Stand up a monitored Windows endpoint in a virtual lab.
  • Enable and read the Windows logs a SOC relies on (Event Viewer).
  • Collect endpoint logs centrally in a SIEM and write custom detection rules.
  • Triage alerts, confirm them with raw evidence, and build an attack timeline.
  • Map activity to MITRE ATT&CK and write an incident report.

2. The scenario: Operation Night Ledger

BlueHarbor Finance is a small (fictional) accounting firm. Your team is its SOC.

At 07:45 this morning the Finance Manager reported that the file Vendor_Bank_Details.csv is missing from the shared finance workstation, and that "the computer felt slow last night." Helpdesk staff member Jamie Santos (j.santos) says they did not log in yesterday evening.

Management wants answers: Did someone break in, and how? What did they do? Was data taken or changed? Can they get back in? What must we fix? You will answer these on Days 4-5.

Read the full brief in 05_Attack_Simulation / Scenario_Brief.md.

Day 1 - Build the lab

Goal: two virtual machines running and able to talk to each other on a private network. Checkpoint: you can ping between the VMs and open the Wazuh dashboard.

1.1 Download everything (do this first)

FILE

02_Lab_Setup / Download_Links.md has every link. Downloads total about 12 GB, so start them before anything else.

DO THIS

  1. Download and install VirtualBox 7.x for your computer.
  2. Download the Wazuh OVA (the ready-made SIEM virtual machine, ~5 GB).
  3. Download a Windows ISO: Windows 11 Enterprise Evaluation (90 days). If your PC cannot run Windows 11, use Windows Server 2022 Evaluation instead.
While downloads run, read 02_Lab_Setup / Lab_Network_Plan.md and fill in the VM specs in your Team Charter.

1.2 Check your computer can run VMs

DO THIS

  1. Reboot into your PC's BIOS/UEFI and make sure virtualization (Intel VT-x / AMD-V) is enabled. Without it, 64-bit VMs will not start.
  2. Make sure you have at least 8 GB RAM and 100 GB free disk.
If a member's laptop is too small, the team uses one strong PC as the "primary lab" and shares its screen during team calls. Decide this today.

1.3 Import the Wazuh server VM

DO THIS

  1. VirtualBox menu: File > Import Appliance. Choose the Wazuh .ova.
  2. Set RAM to 4096 MB (8192 if you can), 2-4 CPUs. Name it CTM-Wazuh. Click Import.
  3. Start the VM. At the login prompt sign in with wazuh-user / wazuh.
  4. Type ip -4 addr and note the address (you will set this up in step 1.5).

1.4 Create the Windows endpoint VM

DO THIS

  1. Machine > New. Name CTM-WIN01, Type Microsoft Windows, Version Windows 11 (64-bit). VirtualBox 7 enables EFI, Secure Boot and TPM for you.
  2. RAM 4096 MB, CPUs 2, disk 64 GB. Attach the Windows ISO.
  3. Install Windows. Create a local admin user named ctmadmin with a password you choose (write it in your Team Charter). Set the computer name to WIN-CTM-01.
To skip the "Microsoft account" requirement during Windows 11 setup, choose the Windows Server option instead, or select a limited-setup/"domain join" path when offered. A local account is all the lab needs.

1.5 Put both VMs on one private network

You need a Host-only network so the two VMs can talk privately, plus NAT so each can reach the internet for updates.

DO THIS

  1. VirtualBox: Tools > Network > Host-only Networks > Create. Leave the default 192.168.56.0/24 with DHCP enabled.
  2. For each VM: Settings > Network. Adapter 1 = NAT. Adapter 2 = Host-only Adapter (select the one you just created). Enable both.
  3. Start both VMs. Find each host-only IP (starts with 192.168.56): on Wazuh type ip -4 addr; on Windows open Command Prompt and type ipconfig.
  4. Record both IPs in your Team Charter.

CHECK

  1. From the Windows VM, open a browser and go to https://<WAZUH-IP>. Accept the certificate warning. Log in with admin / admin. You should see the Wazuh dashboard. In the dashboard menu, open About and record the Wazuh version - you need it on Day 3.

1.6 Take your first snapshots

Snapshots are your safety net. If anything breaks later, you roll back in seconds instead of rebuilding.

DO THIS

  1. For each VM: VirtualBox > (select VM) > Snapshots > Take.
  2. Name them Day1-Clean-Build.

Day 2 - Turn on Windows logging

Goal: make the Windows endpoint record the security events a SOC needs. Checkpoint: Preflight_Check.ps1 shows the logging items as PASS.

Running the scripts. All Day 2-4 scripts run inside the Windows VM. Right-click Windows PowerShell > Run as administrator. If scripts are blocked, run this once in that same window:
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
Then run a script with .\ScriptName.ps1. Copy the CAPSTONE_RESOURCES folder into the VM first (shared folder, or just download it from your shared drive inside the VM).

2.1 Create the company environment

FILE

03_Windows_Logging / Seed_Lab_Environment.ps1

This creates three staff accounts (j.santos, m.reyes, a.cruz) and the C:\CapstoneFinance folder with sample business files. Note: j.santos is given a deliberately weak password - that is part of the story.

DO THIS - run it, then confirm the users appear with Get-LocalUser.

2.2 Enable Windows audit logging

FILE

03_Windows_Logging / Enable_Audit_Logging.ps1

This turns on auditing for logons, account changes, process creation and more; adds the command line to process events; enables PowerShell script block logging; and makes the logs bigger so evidence is not overwritten.

DO THIS - run it. It prints the audit policy at the end; screenshot that.

After this runs, these events start recording: 4624/4625 (logon success/failure), 4720/4732 (account created / added to group), 4688 (process with command line), 4698 (scheduled task), 4104 (PowerShell code). See the cheat sheet below.

2.3 Install Sysmon

FILE

03_Windows_Logging / Install_Sysmon.ps1 and sysmon-capstone.xml

Sysmon adds deep detail: every process (with hashes and parent), network connections, file creation/deletion, registry autostart changes and DNS queries. The script downloads Sysmon from Microsoft and installs it with our tuned configuration.

DO THIS - run it.

CHECK - open Event Viewer > Applications and Services Logs > Microsoft > Windows > Sysmon > Operational. You should see events appearing.

2.4 Import the ready-made Event Viewer views

FILE

03_Windows_Logging / EventViewer_Custom_Views\ (four XML files)

These give you one-click filtered views instead of scrolling through thousands of events.

DO THIS

  1. Open Event Viewer (press Start, type eventvwr.msc).
  2. Right-click Custom Views > Import Custom View...
  3. Import each of the four files: CV1 Authentication, CV2 Account Changes, CV3 Persistence and Execution, CV4 PowerShell and Defender.

2.5 Learn the key Event IDs

Keep 03_Windows_Logging / Windows_Event_ID_Cheat_Sheet.md open while you work. The essentials:

Event IDMeaningWhy it matters

Day 3 - Send the logs to Wazuh (SIEM)

Goal: the Windows endpoint ships its logs to Wazuh, and your custom rules raise alerts. Checkpoint: the agent shows ACTIVE and your test events create alerts.

3.1 Install the Wazuh agent on Windows

FILE

04_Wazuh / Install_Wazuh_Agent.ps1

This installs the agent, points it at your Wazuh server, and adds the extra log sources (Sysmon, PowerShell, Defender) plus File Integrity Monitoring on the finance folder.

The agent version must be the same or older than your Wazuh server version (the one you recorded on Day 1). Pass it with -Version.

DO THIS - in the Windows VM, run (use your own IP and version):

.\Install_Wazuh_Agent.ps1 -WazuhIP 192.168.56.101 -Version 4.9.2

CHECK

  1. The script prints the agent log; look for "Connected to the server".
  2. In the Wazuh dashboard open Agents. WIN-CTM-01 should be ACTIVE (green).
If the agent is not active: check the IP, confirm both VMs are on the host-only network, and that ports 1514/1515 are reachable (run Preflight_Check.ps1 -WazuhIP <ip>). See Troubleshooting.

3.2 Add the custom detection rules

FILE

04_Wazuh / local_rules.xml

These rules (IDs 100200-100210) are the brain of your SOC. They turn raw events into meaningful alerts: brute force, new admin accounts, scheduled tasks, encoded PowerShell, registry persistence, finance-file tampering, and Defender detections - each mapped to MITRE.

DO THIS

  1. In the dashboard: menu > Server management > Rules.
  2. Click Manage rules files, then Custom rules, and edit local_rules.xml.
  3. Keep anything already there. Paste the contents of our local_rules.xml below it. Click Save.
  4. When prompted, Restart the manager (or on the server console run sudo systemctl restart wazuh-manager).
Alternative on the server console: edit /var/ossec/etc/rules/local_rules.xml, then restart the manager. After a restart, check sudo tail -n 50 /var/ossec/logs/ossec.log for rule errors.

3.3 Prove it works (smoke test)

DO THIS - in the Windows VM, generate a couple of safe test events:

  1. Fail a logon on purpose a few times: open PowerShell and run
    runas /user:WIN-CTM-01\j.santos cmd and type a wrong password 3-4 times.
  2. Create and remove a test file in the watched folder:
    "test" | Out-File C:\CapstoneFinance\test.txt ; Remove-Item C:\CapstoneFinance\test.txt

CHECK - in the dashboard go to Threat Hunting (or Discover) and search rule.groups:"ctm_capstone". You should see your alerts. Use the queries in 04_Wazuh / Wazuh_Dashboard_Queries.md.

Day 3 checkpoint
[ ] Wazuh agent ACTIVE in the dashboard
[ ] Sysmon / PowerShell / Defender channels + FIM configured
[ ] Custom rules loaded; manager restarted without errors
[ ] Smoke-test alerts visible under rule.groups:"ctm_capstone"
[ ] Snapshot taken on both VMs: "Day3-Wazuh-Ready"

Day 4 - The incident and your investigation

Goal: detect, investigate and document the intrusion. Checkpoint: a complete attack timeline and all alerts triaged.

4.1 Run the scenario (Red Cell only)

FILE

05_Attack_Simulation / Run_Scenario.ps1

Only the Lab Engineer (Red Cell) or the instructor runs this, inside the Windows VM, as Administrator. They do not read the script or share its output. Everyone else investigates blind, like a real SOC. First take a snapshot named Day4-Before-Attack.

DO THIS (Red Cell): .\Run_Scenario.ps1 - it takes about 6 minutes and prints only "Stage X of 8 complete". Then wait 2-3 minutes for Wazuh to index events.

Plan B. If your live lab is broken (agent never connected, a VM died), use 06_Backup_Dataset\ instead. It contains the exact same incident as CSV and JSON files you can open in Excel and a text editor. Your investigation and report are identical.

4.2 How to investigate (the SOC method)

Work this loop for every alert. Record everything in 07_Team_Templates / 03_Alert_Triage_Tracker.xlsx and 04_Investigation_Worksheet.docx.

  1. Spot - in Wazuh, search rule.groups:"ctm_capstone" and sort by time.
  2. Understand - open the alert; read rule.description, rule.level, MITRE ID, and the event fields (account, command line, file).
  3. Confirm - find the same event in Event Viewer using your custom views. This raw evidence is what goes in the report.
  4. Record - add a row to the triage tracker: time, rule.id, Event ID, true/false positive, severity, MITRE, screenshot name.
  5. Connect - place it on the timeline. Ask: what came before, what came after?
Take a screenshot of every confirmed alert (both the Wazuh view and the Event Viewer entry). Name them like T03_4720_new_user.png. Screenshots are your evidence and your presentation material.

4.3 What to look for (without spoiling it)

The intrusion moves through these ATT&CK stages. Find the evidence for each:

StageQuestion to answerWhere to look
Initial AccessHow did they get in? Whose account?4625, 4624; rule 100201
DiscoveryWhat did they look at?Sysmon 1 / 4688; rule 100206
Privilege / PersistenceNew account? Auto-start? Task?4720, 4732, 4698, Sysmon 13; rules 100202-100207
ExecutionWhat code ran, and was it hidden?4104, Sysmon 1; rule 100205
Collection / ExfilWhat data was staged, changed, deleted, sent out?FIM, Sysmon 11/22/3/26; rules 100208/100210
ToolingDid AV catch anything?Defender 1116/1117; rule 100209

Answer the 15 questions in the Investigation Worksheet. Decode the encoded PowerShell with CyberChef (From Base64) or by reading Event 4104, which logs the decoded code.

5. Troubleshooting

ProblemTry this
VM won't start / 64-bit greyed outEnable Intel VT-x / AMD-V in BIOS. Disable Hyper-V on the host if it conflicts.
VMs can't reach each otherBoth need Adapter 2 = the same Host-only Adapter. Check IPs are both 192.168.56.x.
Scripts are blockedRun Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass in that PowerShell window, as Administrator.
Wazuh agent not ACTIVERun Preflight_Check.ps1 -WazuhIP <ip>. Confirm ports 1514/1515 reachable; restart WazuhSvc; read ossec.log.
Agent version errorAgent version must be <= server version. Reinstall with the right -Version.
Custom rules not firingRestart the manager. Check /var/ossec/logs/ossec.log for XML errors. Test with wazuh-logtest.
No Sysmon eventsConfirm the Sysmon64 service is running; re-run Install_Sysmon.ps1.
Dashboard won't loadGive the Wazuh VM more RAM (8 GB). Wait 2-3 minutes after boot. Use https:// and accept the certificate.
Live lab broke on Day 4Switch to 06_Backup_Dataset and continue the investigation from the files.

Still stuck after 15 minutes? Post in your team channel with a screenshot of the error and what you already tried.

6. Glossary

TermPlain meaning
SIEMSecurity Information and Event Management - software that collects logs and raises alerts (Wazuh).
SOCSecurity Operations Center - the team that watches for and responds to attacks (you).
AgentSmall program on a computer that sends its logs to the SIEM.
SysmonMicrosoft tool that records detailed endpoint activity.
Event IDA number Windows uses to label a type of event (e.g. 4625 = failed logon).
FIMFile Integrity Monitoring - alerts when watched files change.
TriageQuickly deciding if an alert is real and how urgent it is.
True/False positiveA real detection vs. a harmless one.
PersistenceTechniques that let an attacker regain access after a reboot.
MITRE ATT&CKA public catalogue of attacker techniques, each with an ID like T1110.
SnapshotA saved state of a VM you can instantly roll back to.
